## Overview

What 001 delivers: run one command and a window opens showing a coloured
triangle on a dark background. Escape or the close button quits cleanly.

### Files

```
artificial-space/
  CMakeLists.txt
  CMakePresets.json           debug + release build configurations (0.4)
  src/
    main.cpp                  init everything, run the loop, catch fatal errors
    platform/
      GlfwLibrary.hpp/.cpp    GLFW start-up and shut-down (RAII)
      Window.hpp/.cpp         the OS window + its OpenGL context (RAII)
    render/
      Renderer.hpp/.cpp       loads OpenGL, owns the triangle, draws a frame
      ShaderProgram.hpp/.cpp  compiles + links a vertex/fragment pair (RAII)
      Buffer.hpp/.cpp         a block of GPU memory (RAII)
      VertexArray.hpp/.cpp    describes how vertex data is laid out (RAII)
      GlDebug.hpp/.cpp        OpenGL debug-message callback
  shaders/
    triangle.vert
    triangle.frag
  external/glad/              generated by Lyra (see Part 2)
```

No `Input` class yet. See [1.4](#14-input-for-001).

### The whole program at a glance

```
main()
  try
    GlfwLibrary glfw          ← GLFW initialised
    Window window             ← OS window + OpenGL 4.5 context
    Renderer renderer         ← glad loads GL, triangle uploaded to GPU
    run(window, renderer)     ← the loop, until quit
  (scope ends: destroyed in REVERSE order:
     renderer → GPU objects freed while the context still exists
     window   → context + window gone
     glfw     → GLFW shut down)
  catch → print the error, exit with failure
```

The reverse destruction order is the core reason for RAII here. C++
guarantees it, so cleanup happens in the right order without us writing any
cleanup code. More in [1.2](#12-ownership-and-start-up-order).

### 0.3 The CMakeLists, in outline

```cmake
cmake_minimum_required(VERSION 3.28)
project(artificial-space LANGUAGES C CXX)     # C because glad is C

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)          # fail rather than silently use older C++
set(CMAKE_CXX_EXTENSIONS OFF)                # -std=c++23, not -std=gnu++23

# Default to a Debug build when none is given
# glad   → small static library from external/glad
# glfw   → find_package
# artificial-space → our executable, links glad + glfw
# warnings: -Wall -Wextra -Wpedantic -Wconversion -Wshadow (our code only, not glad)
# Debug only: -fsanitize=address,undefined  -g
# shaders/ copied next to the executable after each build (see 0.5)
```

**Why these choices:**
- **`CMAKE_CXX_EXTENSIONS OFF`:** GCC's "gnu" mode allows non-standard
  extensions. Turning it off keeps us writing portable, standard C++.
- **Warnings only on our code:** glad is generated code. Its warnings would
  be noise we can't (and shouldn't) fix.
- **`-Wconversion -Wshadow`** go beyond the agreed `-Wall -Wextra -Wpedantic`.
  They catch silent `double`→`float` and `int`→`unsigned` conversions, and a
  variable hiding another. Conversions in particular will matter for physics.
  **Agreed (Lyra): keep them**, to catch issues early.
- **UBSan (`undefined`) alongside ASan:** catches undefined behaviour
  (signed overflow, bad casts) at runtime. It's almost free to add.
- **glad as its own library target:** keeps C and C++ separate, and lets
  the warning flags apply only to our code.

With two **CMake presets** (a small `CMakePresets.json` that names each

```
cmake --preset debug   && cmake --build --preset debug     # → build/debug/    (dev, sanitizers on)
cmake --preset release && cmake --build --preset release   # → build/release/  (optimised, what gets copied to the main PC)
```

How `build/release/` gets to the main PC is up to Lyra and isn't documented.

**Agreed (2026-11-03):** debug + release presets. `shaders/` ships inside the
release folder. Release is effectively "pre-alpha". Versioning comes later,
once there's a game to version (Lyra thinking about it). The commands are
mirrored in the README's Building/Running sections. Keep them in sync.

**Why two configurations:** the Debug build links the sanitizer runtimes
(`libasan`, `libubsan`) and runs 2–3× slower. That's great for catching bugs
while developing, but you don't want it as the thing you play. Release is
optimised (`-O2`) with no sanitizers. **Why presets:** without them you type

two builds can drift apart. Presets are a CMake-standard file, so editors and
clangd understand them too.

**Agreed (Lyra):** the agent may run configure, build, run and test commands.

### 0.5 Making `build/release/` runnable on another machine

Copying an executable to another Linux machine works only if everything it
needs at runtime is either **inside the folder** or **already on that
machine**. Three things to handle:

**1. Shaders: copy them into the build folder, find them next to the
executable.**
The original plan baked the *absolute* path of `shaders/` into the
program. On the main PC that path doesn't exist, so it would fail.

| Option | For | Against |
|---|---|---|
| **Copy `shaders/` into the build folder at build time. The program finds them relative to its own executable** (agreed) | The folder is self-contained. Works wherever it's copied. Shaders are still plain files you can edit | Finding "my own executable" is OS-specific (`/proc/self/exe` on Linux). It lives in `platform/` |
| Relative to the current working directory | Simplest | Breaks if you start the game from any other folder |
| Bake shader source into the executable as strings | Nothing to copy at all | Rebuild to change a shader. C++23 has no clean way to embed files (`#embed` is C++26) |

**2. GLFW: the main PC needs it, or we bundle it.**
Debian only ships GLFW as a *shared* library (`libglfw.so.3`), so the
executable expects to find it on whatever machine it runs on.

| Option | For | Against |
|---|---|---|
| **A. Main PC installs `libglfw3` from apt** | No change for us. Tiny install | The running machine must have GLFW **3.4** (LMDE/Debian 13 does, some older distros ship 3.3) |
| **B. Build GLFW from source and link it statically into our executable** | Nothing to install on the main PC. Exact same GLFW everywhere | GLFW source goes in `external/` (Lyra downloads it). The VM needs X11/Wayland dev headers to build it. Drops the "system package" decision from 001 planning |

**Agreed (2026-11-03): A for now.** GLFW 3.4 is a runtime requirement on the
running machine. Lyra's long-term goal is plug-and-play (no installs), so **B**
is tracked as [T0001](../../tickets/T0001-glfw-static.md).

**3. glibc: the C runtime is the one thing we can't bundle.**
A program built against glibc 2.41 (Debian 13) refuses to start on a system
with an *older* glibc. Newer is fine. **Resolved for Lyra's setup:** the main
PC runs current LMDE, which is built on the same Debian 13 base, so glibc and
GLFW 3.4 match the VM exactly. On other machines, the fix for an older glibc
would be building inside an older environment (e.g. a container). That's not
needed now.

**Not a concern:** the GPU driver. glad loads OpenGL from whatever driver
the running machine has, so the same executable uses llvmpipe on the VM and
the real GPU on the main PC. Same for X11 vs Wayland: GLFW 3.4 picks at
runtime.

## Part 1: Main and the game loop

Lyra's shape from ARCHITECTURE.md: **main** inits and hands off to the
**loop**, and the loop does **input → tick → render**.

### 1.1 main.cpp

```cpp
int main()
{
    try {
        GlfwLibrary glfw;
        Window window{{.width = 800, .height = 600, .title = "Artificial Space"}};
        Renderer renderer{window.gl_loader()};

```

- **Designated initialisers** (`.width = 800`) name each field, so you can
  see what the numbers mean.
- **`std::println`** (C++23) is type-safe formatted printing, like Python's
  f-strings. No `printf` format-string bugs.

    Will this load into fullscreen?

### 1.2 Ownership and start-up order

Three things must happen in a strict order:
1. GLFW initialised → 2. window + context created → 3. glad loads OpenGL
→ 4. GPU objects created.

Shut-down is the exact reverse, and that matters: deleting a GPU buffer after
its context is gone is undefined.

**Decision:** each step is an object, declared in that order in `main`.
**Why:** C++ constructs locals top to bottom and destroys them bottom to
top, even when an exception is thrown halfway. If the window fails to open,
GLFW is still shut down properly. We get correct ordering *and* correct
cleanup-on-failure without writing either. Alternatives considered:
- **`init()`/`shutdown()` functions:** easy to forget one, or call them in
  the wrong order, especially on error paths.
- **One big `Game` class owning everything:** works, but members are
  destroyed in reverse *declaration* order, which is easy to get wrong
  silently. And it's structure ahead of need.

`main` owns everything, and `run()` borrows by reference (as per
ARCHITECTURE rules).

**Agreed 2026-11-03** (walked through). The compiler decides *when*
destructors run (reverse order, on every exit path, including exceptions,
via unwind tables). We decide *what* they do by writing them. Members are
destroyed automatically after the destructor body, so `Renderer` (which only
holds wrappers) can probably use the compiler-generated destructor.

### 1.3 The loop

```cpp
void run(Window& window, Renderer& renderer)
{
    while (!window.should_close()) {
        // -- input --
        window.poll_events();
        if (window.is_key_down(Key::Escape)) window.request_close();

        // -- tick --
        // nothing yet: fixed timestep arrives in feature 005

        // -- render --
        renderer.draw(window.framebuffer_size());
        window.swap_buffers();
    }
}
```

**Where it lives:** a free function in `main.cpp`. **Why:** it's ~15 lines.
A `Loop` or `Game` class would be structure ahead of need. It moves out when
tick gets real (005).

**Decisions inside the loop:**
- **VSync on (`glfwSwapInterval(1)`).** `swap_buffers()` waits for the
  monitor's next refresh. **Why:** without it the loop spins as fast as it
  can, pinning a CPU core and the GPU at 100% for no visible gain, and it can
  cause tearing. Cost: frame rate is capped at the refresh rate, which
  is what we want anyway. (Even with a powerful GPU, rendering 2000 frames a
  second of a triangle just heats the room.)
- **Window size is asked for every frame, not pushed by callback.**
  `framebuffer_size()` returns the current pixel size, and the renderer sets
  its viewport from it. **Why:** no callbacks, no shared mutable state, and
  data flows one way (platform → render), which matches the ARCHITECTURE
  rules. The cost is one cheap function call per frame.
- **No frame timing yet.** Nothing uses delta-time until 005.

**Agreed 2026-11-03** (walked through): VSync on, size asked for every frame, no timing yet.

### 1.5 Platform classes

**`GlfwLibrary`:** constructor sets the GLFW error callback (see 3.2) and calls
`glfwInit()`, throwing on failure. Destructor calls `glfwTerminate()`.
Non-copyable, non-movable: there's exactly one, and it never moves.

**`Window`:** constructor asks GLFW for:
- OpenGL **4.5 core profile** (no deprecated old-style GL available)
- a **debug context** in Debug builds (needed for 3.3)
- then creates the window, makes its context current, turns on VSync.
Throws if creation fails (e.g. the driver can't do 4.5). Destructor calls
`glfwDestroyWindow`. Non-copyable, movable.

Public interface (all of it):
`should_close()`, `request_close()`, `poll_events()`, `swap_buffers()`,
`is_key_down(Key)`, `framebuffer_size()`, `gl_loader()`.

## Part 2: Rendering engine

### 2.1 What actually happens on the GPU

To draw anything, OpenGL needs four things:

```
 vertex data (CPU)                          on the GPU
 ┌─────────────────┐   upload    ┌──────────────────────────┐
 │ 3 × {pos, color}│ ──────────▶ │ Buffer   raw bytes        │
 └─────────────────┘             │ VertexArray: "bytes 0–11  │
                                 │   are position, 12–23     │
                                 │   are colour"             │
                                 │ ShaderProgram:            │
                                 │   vertex shader  → where  │
                                 │   fragment shader→ colour │
                                 └──────────────────────────┘
                                         draw call: "3 vertices, as a triangle"
```

The **vertex shader** runs once per corner and outputs its position. The GPU
fills in every pixel inside the triangle and **interpolates** the corner
colours across it. The **fragment shader** runs once per pixel and outputs
the final colour. That interpolation is why the triangle comes out as a
smooth gradient.

### 2.2 The RAII wrapper pattern

Every OpenGL object is just a number (`GLuint`) the driver gave us. Each
wrapper class follows the same pattern:

```cpp
class Buffer {
public:
    explicit Buffer(std::span<const std::byte> data);  // glCreateBuffers + upload
    ~Buffer();                                         // glDeleteBuffers

    Buffer(const Buffer&) = delete;                    // no copies
    Buffer& operator=(const Buffer&) = delete;
    Buffer(Buffer&& other) noexcept;                   // moves allowed
    Buffer& operator=(Buffer&& other) noexcept;

    GLuint id() const { return m_id; }
private:
    GLuint m_id = 0;
};
```

**Why non-copyable:** a copy would hold the same number, so two destructors
would delete the same GPU object twice. **Why movable:** so a wrapper can be
returned from a function or stored in a `std::vector`. A move hands the
number over and sets the source to `0`, and deleting `0` is a no-op in
OpenGL. This is C++'s **move semantics**. We'll go through it properly when
we build it.

| Option | For | Against |
|---|---|---|
| **Hand-written per class** (recommended for 001) | Each one is readable on its own. Writing it three times is how the pattern sinks in | Some repetition |
| A generic `GlHandle<DeleteFn>` template | Write the move/delete logic once | More abstract to read before the pattern is familiar |

**Agreed 2026-11-03: hand-write all three now.** Once the repetition is
annoying, we refactor to a template together
([T0003](../../tickets/T0003-gl-handle-template.md)). It's a good C++
templates lesson.

### 2.3 Classes

**`Renderer`:** the only class `main` sees from `render/`.
- Constructor takes the loader from `Window`, calls glad, and **checks the loaded
  version is ≥ 4.5** (throws if not). Then it installs the debug callback
  (Debug builds), loads the shaders, and uploads the triangle.
- `draw(FramebufferSize)`: set viewport → clear to a dark blue-black → bind
  program + vertex array → draw 3 vertices.
- Owns `ShaderProgram`, `Buffer`, `VertexArray` as members.

**`ShaderProgram`:** constructed from two file paths. Reads both, compiles
each, links them. Any failure throws with the file name and the driver's error
log (see 3.4).

**`Buffer`:** `glCreateBuffers` + `glNamedBufferStorage` (fixed size,
uploaded once).
- **Why `Storage` not `Data`:** storage is *immutable* in size. The driver
  knows it'll never be resized and can optimise. The triangle never changes.

**`VertexArray`:** records "attribute 0 = 3 floats at offset 0, attribute 1 =
3 floats at offset 12, stride 24, read from this buffer" using the 4.5
`glVertexArray*` calls.

**Why 4.5 "DSA" calls throughout:** older GL makes you *bind* an object
(make it "the current one") before editing it, which is hidden global state.
DSA (`glNamedBufferStorage(id, …)`) edits the object by name, the way normal
code works. That's the main thing 4.5 bought us.

### 2.4 Glad loading: keeping GLFW and GL apart

glad needs a function that finds GL functions by name. GLFW provides one
(`glfwGetProcAddress`). The question is who calls glad:

| Option | For | Against |
|---|---|---|
| **`Window::gl_loader()` hands GLFW's lookup function to `Renderer`, which calls glad** (recommended) | GLFW stays in `platform/`, GL stays in `render/`, matching the "no raw GL outside `render/`" rule | One small hand-off |
| `Window` calls glad itself | Fewer moving parts | Puts GL loading in the platform layer, breaking the rule |

The hand-off is a **function pointer**: we pass a function itself as a
value. Another C++ concept we'll go through.

### 2.5 Vertex data and shaders

```cpp
struct Vertex { std::array<float, 3> position; std::array<float, 3> colour; };

constexpr std::array<Vertex, 3> triangle{{
    {{-0.5f, -0.5f, 0.0f}, {1.0f, 0.3f, 0.2f}},   // bottom left,  red-ish
    {{ 0.5f, -0.5f, 0.0f}, {0.2f, 1.0f, 0.4f}},   // bottom right, green-ish
    {{ 0.0f,  0.5f, 0.0f}, {0.3f, 0.5f, 1.0f}},   // top,          blue-ish
}};
```

- Positions are in **clip space**: −1 to 1 on each axis, the screen's
  edges. No maths library or camera needed (that's 002–003).
- **`constexpr`:** the data is built at compile time and baked into the
  program.
- **Interleaved** (position, colour, position, colour…) rather than two
  separate arrays. **Why:** it's the common layout and keeps a vertex's data
  together. For 3 vertices it makes no difference to speed.
- **Known quirk:** the triangle stretches when the window is resized,
  because clip space always spans the whole window. Fixing that is the
  camera's job (003).

Shaders (`#version 450 core`): the vertex shader takes `position` (location 0)
and `colour` (location 1), outputs the position, and passes the colour on.
The fragment shader writes the interpolated colour.

**Loading:** `<executable's folder>/shaders/` + file name via
`std::filesystem::path` (see 0.5.1), read with `std::ifstream`. A missing file
throws with the full path. The executable's folder comes from `platform/`
(e.g. a small `executable_dir()` function), so nothing OS-specific leaks into
`render/`.
**Why runtime files, not baked-in strings:** you can edit a shader and rerun
without recompiling, and later we could reload them live.

## Part 3: Error handling

Errors come from five places, and each needs its own approach.

### 3.1 Fatal start-up errors → exceptions, caught in `main`

GLFW won't start, the window won't open, GL is older than 4.5, a shader is
missing or won't compile. The program can't continue in any of these cases.

| Option | For | Against |
|---|---|---|
| **Exceptions** (recommended, and already in the ARCHITECTURE rules) | Constructors can fail directly. RAII cleans up whatever was already built. One `catch` in `main` | Hidden control flow: you can't see from a call that it may throw |
| `std::expected<T, Error>` (C++23) | Errors are visible in the return type, so you can't ignore them | Constructors can't return it, so every class needs a `create()` factory. Lots of plumbing for errors that all mean "quit" |
| `std::abort()` / print-and-exit | Simplest | Skips destructors, so no ordered cleanup |

**Recommendation:** throw `std::runtime_error` with a clear message (what
failed, and why if we know). **Why `runtime_error` and not a custom
type:** nothing catches specific error types yet, only `main` catching
everything. A custom type is structure ahead of need. **`std::expected`'s
turn** comes with *recoverable* errors later: a missing save file, a bad star
data file, a shader reload that fails while the game keeps running.

**Rule kept:** no exceptions inside the loop. `main`'s `catch` is still there
as a safety net.

**Agreed 2026-11-03.** Who throws:

| Who | When |
|---|---|
| `GlfwLibrary` | `glfwInit()` fails |
| `Window` | `glfwCreateWindow` returns null |
| `Renderer` | glad can't load GL, or the version is < 4.5 |
| `ShaderProgram` | file missing, compile fails, link fails |

Callbacks (3.2, 3.3) only print the library's detailed message. Our code
throws a short summary afterwards.

### 3.2 GLFW errors → error callback

GLFW reports problems through a callback, not return values. We install one
(in `GlfwLibrary`, *before* `glfwInit()` so init failures are reported too)
that prints `glfw error <code>: <description>` to stderr.

**Important:** the callback **must not throw**. GLFW is C code, and an
exception passing through C code is undefined behaviour. Print only. The
function that failed (e.g. `glfwCreateWindow` returning null) is what throws.

### 3.3 OpenGL errors → debug output (Debug builds)

| Option | For | Against |
|---|---|---|
| **`glDebugMessageCallback`** (4.3+, recommended) | The driver *tells* us what's wrong, in words, at the call that caused it | Needs a debug context. Some driver overhead (Debug builds only) |
| `glGetError()` after calls | Works everywhere | Just a number. You have to check after every call to find which one failed |

**Setup:** debug context (1.5) + `GL_DEBUG_OUTPUT` +
`GL_DEBUG_OUTPUT_SYNCHRONOUS`. **Why synchronous:** the callback then fires
*inside* the bad GL call, so a debugger's stack trace points straight at it.
The callback prints source, type, severity and message, and skips
"notification" severity (chatty info, not errors). It doesn't throw, for the
same reason as 3.2.

This is one of the main reasons we picked 4.5 over 4.1.

### 3.4 Shader compile/link errors → exceptions with the driver's log

After compiling, check `GL_COMPILE_STATUS`. If it failed, fetch the info
log and throw `"triangle.frag failed to compile:\n<driver log>"`. Same for
linking (`GL_LINK_STATUS`). **Why the file name:** the driver log only says
"line 7", so we add which file.

### 3.5 Memory and undefined behaviour → sanitizers (Debug builds)

ASan catches use-after-free, buffer overruns and leaks. UBSan catches undefined
behaviour. Both report at the moment it happens.

**Known noise:** Mesa and X11 sometimes "leak" small allocations on purpose
(freed by the OS at exit). LeakSanitizer may report these at shutdown. If it
does, we add a small suppression file for *their* libraries only, never for
our code. **Update (build):** it does. Lyra chose to leave it unsuppressed and
treat it as a known baseline. See Build notes.

## Build notes (2026-11-03)

Lyra asked the agent to build all of 001 in one go and then review it. Small
details that the doc didn't spell out or that came out differently, for
Lyra to check in review:

- **Extra platform headers:** `platform/WindowTypes.hpp` holds the two plain
  types that cross into `render/` (`FramebufferSize`, `GlLoader`), so
  `render/` never includes `Window.hpp` or GLFW. `platform/ExecutablePath.*`
  is the `executable_dir()` from 2.5. `platform/Key.hpp` holds the `Key` enum.
- **`Renderer` takes the shader folder** as a second argument
  (`executable_dir() / "shaders"`, passed by `main`), so `render/` stays free of
  OS-specific code (2.5).
- **Load OpenGL before the members:** members are constructed before the
  constructor body runs, so glad is loaded through the first-declared member
  (`m_gl_version{load_opengl(loader)}`). The order is commented in `Renderer.hpp`.
- **`draw()` is `const`**, and `run()` takes `const Renderer&`, to back up
  "render never mutates state".
- **`ShaderStage`:** a small private RAII helper in `ShaderProgram.cpp` for the
  individual compiled shaders, so a failing fragment shader doesn't leak the
  vertex one.
- **Start-up prints one line** to stderr: `OpenGL 4.5 on <renderer>`. It shows
  at a glance whether we got llvmpipe or the real GPU (checklist 4.2).
- **Release is `-O2`**, set in the preset. CMake's own Release default is `-O3`.
- **GL debug output is always "enabled"** by `Renderer`, but it checks the context
  flags and does nothing without a debug context, so there's no `#ifdef` in
  `render/`. `Window` requests the debug context only when `NDEBUG` isn't
  defined (Debug builds).
- **`.clangd`** (added after Lyra's editor reported `'platform/Key.hpp' file
  not found`): clangd didn't know about `-I src`, because CMake writes
  `compile_commands.json` into `build/debug/`, where clangd doesn't look. A
  two-line `.clangd` points it there. The symlink alternative was rejected
  (fiddly in git).
- **Leak reports on exit (3.5): left as is (Lyra, 2026-11-03).** The Debug
  build's exit code is 1 because of LeakSanitizer, even when our `main` returns 0.
  The **expected baseline** on the dev VM (Mesa llvmpipe):
  - ~100,956 bytes in 449 allocations from inside `glfwCreateWindow`
    (confirmed as `libGLX_mesa.so` by preloading it)
  - plus 2 × 56 bytes from inside the driver during `glDrawArrays`
    (`Renderer.cpp`), only when frames are drawn
  None of it is from our code. It shows as "unknown module" because GLFW
  unloads the driver at `glfwTerminate`. Anything *beyond* this baseline is
  worth a look. Investigated and dropped: a suppression file (works for the
  `glfwCreateWindow` part only with `fast_unwind_on_malloc=0`, and can't name
  the draw-time leaks without naming our own `Renderer::draw`).
